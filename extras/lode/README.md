# lode themes

Generated by `scripts/build lode` — one file per style, 48 in all. The generator
is `lua/lvim-colorscheme/extra/misc/lode.lua`.

Install:

```sh
mkdir -p ~/.config/lode/themes
cp extras/lode/*.toml ~/.config/lode/themes/
```

Then pick one in lode's Theme menu, or set `LODE_THEME` to a file's stem
(`LODE_THEME=LvimBase_dark`). `$LODE_THEME_DIR` overrides the search path, and
the first directory wins a name clash.

## This target does no contrast work. On purpose.

Every other target under `extra/` reads the raw palette and floors each
foreground against the surface it lands on. **This one does not.** It reads
lvim-colorscheme's *resolved highlight groups* and copies them unchanged —
`surface.base` is `Normal.bg`, `text.primary` is `Normal.fg`, `surface.status` is
`StatusLine.bg`, and so on down the file — including the pairs that measure below
4.5:1.

The first version of this generator did follow the family rule, and its output
was correct and did not look like lvim. On base dark it emitted the palette's
backgrounds exactly, and lifted the body text from `#5e8888` (3.86:1, which is
what `Normal.fg` is, deliberately: an editor's body text under syntax
highlighting is not a web page's) to `#6cbaba` at 6.76:1. That one step up the
lightness scale was the whole difference between "our theme" and "a theme built
from our colours".

lode is a database client meant to sit beside the editor all day. It has to be
the same colour as the editor, so the SOURCE changed rather than the mathematics
being deleted.

**Do not "fix" this in a later audit.** A sweep that adds `ensure_contrast` here
undoes the only thing this target is for. The generator's header says the same
thing, at the top, for the same reason.

## Checking them

```sh
python3 extras/lode/check.py        # summary per theme
python3 extras/lode/check.py -v     # every measured pair
```

`check.py` **reports and does not gate**. It prints every ink/surface pair the
client actually paints, marks the ones under 4.5:1, and exits 0 — those pairs are
the editor's own and are not faults. It *does* fail on a theme that is
structurally broken: a missing role, a value that is not `#rrggbb`, a `dark` flag
that disagrees with the style's own name, or a name that does not match the file.

Across the 48 styles it currently reports around a thousand pairs under the line.
That number is a property of the editor's palettes, not a to-do list.

## Roles with no analogue in an editor

Named here rather than left to be guessed at:

- **`grid.row_alt`** — an editor has no alternating rows. `ColorColumn` is the
  nearest: a quiet band over the buffer background, not a second surface.
- **`surface.border`** — `WinSeparator.fg`, which on every lvim style equals its
  own background. The editor draws no line between windows, so the client's
  frames are invisible too and its structure is carried by the surfaces. That is
  the editor's look, copied.
- **`grid.line_nr`** — `LineNr.fg`, used for the row-number column and nothing
  else, because that column is literally a line number. It is as quiet here as
  the gutter is there (around 1.2:1). Every *other* small label — section
  headings, driver names, counters, the status strip — uses `text.muted`, which
  is `Comment`: both are "quiet" in the editor and they are not interchangeable.
- **`match.*` and `syntax.*`** are carried although the client does not paint
  with them yet. The file is the contract; a role dropped because today's client
  has no use for it is a role the next version has to re-derive from somewhere
  else.
